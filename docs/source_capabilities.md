# NARの取得条件と実測 — 2026-09-30

## 現在の結論

- **Macから少数の公式ZIP・HTMLサンプルを取得できた。** HTTP200、原本保存、UTF-8 BOMの解析、異なる取得時点の履歴・as-ofを実測した。内容が同じでも別の観測を残す。
- **CloudflareからのNAR取得は未成功。** 2026-09-29の2回はHTTP404。同じURL・研究UA・AcceptでのMac対照は200だったが、時刻差があり原因は未確定。恒久的な拒否や申請必須とは断定しない。
- 通常の公開ZIP取得に登録・申請が必須という記載は、確認した説明書にはない。定期自動取得・私的な継続クラウド保存への条件適用は未解決。少数サンプルの成功を無条件の許諾と扱わない。
- ユーザーは問い合わせを前提にせず低頻度・少数サンプルで研究を進める範囲を承認済み。登録・問い合わせ送信は人が行う。現時点の新たな依頼はない。[人に依頼する範囲](human_actions.md)

## 取得・保存の実装境界

| 能力 | 状態 |
|---|---|
| capture_mode | `poll_snapshot`。観測履歴は自前で追記する |
| NAR公式のupstream_history / backfill | 全更新履歴の配布は未検証。第三者の履歴表示とは区別する |
| 頻度 | Macの有限計画は要求間隔を全種共通で120秒以上に制限。常時収集ではない |
| ZIP | 複数競走・券種を含む一配布物を一度取得して内部で分配。買い目のゼロ・欠落・範囲表示を区別 |
| 時刻 | 取得開始・ヘッダー受信・本文受信・原本/receipt保存・索引登録・解析・利用可能時刻を分離 |
| source_updated_at | 公式CSVの市場更新時刻は不明なのでnull。ファイル名UNIX時刻や取得時刻で代用しない |
| 同値と再配送 | 別取得は同じ本体でも別観測。同一イベントの再配送は通信・観測・判断を増やさない |
| 月次 | `FINAL_ONLY`。今回の有限取得コマンドは当日だけ。月次実ファイルは未取得 |
| CloudflareからNARへの直接取得 | 失敗2件、成功ZIP/観測0件。収集false、空枠、Cronなし、公開URL/previewなしで停止中。Mac原本のクラウド取込み・解析実績はstatusへ別記 |
| 公開境界 | 原本・実データ・詳細出力・台帳・SecretsをGit/CI/PRに出さない |

Macでは承認済みの有限サンプル経路を使用し、Cloudflareの停止状態を変えない。`collect-sample`と`paper-session`は同じ取得処理を使い、同じprivate rootで間隔・停止状態を共有する。リダイレクトや自動再試行は行わず、拒否・CAPTCHAで停止、429はRetry-After以上待機する。未取得期間を後の断面で埋めない。[実データ手順](real_data_runbook.md)

## 状態・払戻の実物確認

- 公式単複ページの最終見出し、競走除外、日付のない`HH:MM現在`を確認。最後の表示は日付が確定できないため`source_updated_at=null`。空欄から発売中や出走有効を推定しない。
- [結果・払戻の説明](https://www.keiba.go.jp/beginner/step6.html)は確定後の100円当たり払戻を案内し、除外馬を含む馬番号の組合せは全額返還とする。枠式には別条件がある。
- [異常時の表記説明](https://www.keiba.go.jp/beginner/step2.html)では、発売前の出走取消、主に発売後の競走除外と返還、出走済みの競走中止と返還なしを区別している。
- 成績実例で通常馬連・三連複払戻と除外返還を正規化した。数値着順は掲載組番の整合確認に使い、払戻額は計算しない。同着・特払い・不成立・枠式の自動適合は未完了。重勝式用の取消・除外馬番欄を通常馬連の返還根拠へ流用しない。

取得・モデル・Paper・Cloudflareの進捗は [status.md](status.md)。過去の「未取得」「人の取得待ち」はGit履歴に保持し、現在の停止条件とはしない。

## 第三者の過去履歴の少数確認（2026-09-30）

[keibaoddsの地方競馬画面](https://keibaodds.com/nar)で、前日を指定し、登録せずに単勝・馬連・馬単の中間履歴を閲覧できた。
[利用規約](https://keibaodds.com/privacy)も確認した。今回の少数の公開画面確認を、継続的・大量の自動取得の許可へ拡張しない。

最初の2競走では、単勝は9/10の中間時点、馬連・馬単は各2時点と、別枠の最終値が表示された。
12頭に必要な馬単132組・馬連66組に対し、確認した組合せ履歴は各時点50組だった。
画面にも「収録済みの人気順データ」とあり、表示のない組合せを無投票・ゼロとは解釈しない。
発走10分前に利用できる直近表示も13分以上古く、既存の300秒の鮮度条件を満たさなかった。
一つ目の表を非公開保存し、二つ目は収録範囲を記録。いずれもモデル計算・仮想購入・収益性評価には使っていない。

時刻表示の意味、当時の公開遅延、予定変更履歴は未検証。画面を取得した現在の時刻を、過去の利用可能時刻へ戻さない。
これは第三者に中間履歴の表示があるという確認で、NAR公式の全更新履歴の有無を確定するものではない。

次に、保存済み公式競走情報から7頭以下の唯一の競走を、結果や価格差を使わずに追加選択した。
単勝7頭・馬単42組・馬連21組が揃う中間断面を確認し、表の保存内容を画面からの読出しとチェック値で照合した。
ただし直近表示は固定した判断時刻と同じ分で、秒・公開遅延は不明。「その分の開始時点で利用可能」という
仮定付きでだけ既存モデルを計算した。60秒の遅延を置くと、次に使える断面は31分古く、馬単も不完全になる。
公式成績1件を共通の有限取得処理でHTTP200取得し、既存精算処理を一時的な計算用ストアで再利用した。
オンラインPaperの判断・精算件数は増やしていない。厳密な時点再現や収益性を示すバックテストは未達成。

### 定期蓄積用の公開JSON経路

ユーザーから過去履歴の定期蓄積を依頼され、同サイトの公開HTMLと参照JavaScriptを確認した。
画面は `/odds` に `race_kind=nar`、`race_date`、`page`、`display_times` 等を付けて読み込む。
画面と同じ最大24時点の要求で、認証・CookieなしのHTTP200をMacとCloudflare Browser Renderingで確認した。
これは公開画面の実装経路であり、別途保証された公式APIとは扱わない。
Browser Renderingの画面全体は2回タイムアウトしたが、JSON経路は成功。コネクターの返値は途中で切れたため、その返値を保存原本とは数えない。
Mac側では約80KBの完全なJSONを取得し、複数競走・券種の履歴と「最終」ラベルを確認した。

[robots.txt](https://keibaodds.com/robots.txt) はCloudflareからHTTP200で取得し、全パスを許可する内容だった。
[利用規約](https://keibaodds.com/privacy) には商業利用やサービス運営を妨げる行為の禁止がある。
個人研究として、取得完了から5分以上の間隔・同時1件・完了ページの重複取得なしで蓄積する。
登録・問い合わせ送信・規約への追加同意・有料契約は行っていない。
取得件数や時刻の精度は[状態報告](status.md)へ記録し、時刻ラベルだけで厳密な過去as-ofを再現できるとは判断しない。

同じ過去日・先頭ページでも、別時刻のMac取得とCloudflare取得で総件数と競走集合が異なった。
時刻差・経路差があり原因は未確定。原本と取得時刻を保持し、全ページ保存だけで日全体の完全性を断定しない。
