# Cloudflareでの当日収集

既存の`hr-platform-dev-ingestion`、`hr-platform-dev-research`、非公開R2・D1を使う。設定の作成と実稼働は区別し、現在の実測は[status.md](status.md)へ記す。

## 処理

- 収集用のDurable Objectを提供元に一つ置く。Cloudflareのalarmが次の取得を起動し、MacやCodexの常時起動に依存しない。
- 日付が変わると最初に当日のレース情報ZIPを取得する。全場のレース一覧・出走情報・結果・払戻表示を、既存CSVパーサーで保存する。
- 原本、取得試行、観測、解析版をR2・D1に保存する。同値の再観測も残し、同じイベントの再配送は再取得しない。
- 収集DOは取得・原本保存だけを行う。次のalarm保存後に研究Workerへ解析を通知する。毎分Cronも同じ未解析原本の選択・D1リースを使い、解析・モデルの失敗や長い待機で取得を止めない。受信時刻が新しい原本を優先し、同時刻の場合だけレース情報を先にする。過去のレース情報の移送で新着オッズを待たせず、失敗した解析の原本も残す。
- オッズとレース情報は一つのHTTP入口・停止/待機状態を使う。403等の拒否・CAPTCHA・HTML異常応答で停止し、429ではRetry-After以上待つ。停止を定期処理から解除しない。
- alarmが取得窓を過ぎたら欠測を記録する。後の取得を停止期間の過去断面として扱わない。

## 設定

取得間隔・有効な取得窓は`configs/collection.json`、時間帯・レース情報の再取得間隔・URL・HTTPの上限は`configs/cloud-collection.json`に置く。現案は毎日07:00〜23:00 JST、要求完了から120秒以上空ける。30分ごとのレース情報取得はオッズ取得の1回分を使うため、その前後のオッズ間隔は通常より長くなる。全更新や厳密な2分周期を保証する設定ではない。

`DAILY_COLLECTION_ENABLED`、`COLLECTION_ENABLED`、`SOURCE_APPROVED`が全てtrueの場合だけ日次収集する。収集のCronは毎時の起動確認に使い、同じDurable Objectのalarmが既にあれば重複起動しない。研究Workerは原本保存後の非公開通知と毎分Cronで未解析原本を確認し、同じ観測・解析版の同時処理をD1のリースで抑える。既存の有限サンプルモードは日次スイッチfalseのときにだけ使う。公開HTTPとpreviewは無効のままとする。

非公開Service bindingの`CollectionControl`から、`collectSample(slot)`で設定済みの有限枠を診断し、`ensureDaily()`で日次alarmを初期起動できる。両方とも既存の取得・停止・待機処理へ委譲し、停止解除機能は持たない。有限枠のRPCとCronが重なっても同じイベントとして扱う。初期起動後にローカルの接続を終了してもalarmはCloudflare内で継続する。

## 確定オッズ

`MONTHLY_COLLECTION_ENABLED=true`では、同じ収集DOが公式の月次オッズZIPも取得する。[公式説明書](https://www.keiba.go.jp/pdf/manual/data_pdf_manual.pdf)では毎夜更新され、競走成績が確定した値を含む。月末まで待つ必要はない。月次の時刻と要求間隔は`configs/cloud-collection.json`に置き、現設定は10:00 JST以降・失敗を含め前回のCloudflare処理の終了側の時刻から24時間以上とする。月初1日は前月、2日以降は当月を指定する。これは締切直前のオッズ更新を取得する機能ではない。

公式の取得頻度の推奨は「月次ファイルは1日に1回を上限」で、14:10という時刻や厳密な24時間待機は当方の設定だった。初回の10月分は、前日のMacによる9月分取得とは日付・対象月が異なり、当日の月次取得がないことを確認して前倒しする。以後はCloudflareの24時間間隔を維持し、同じ日の再取得、停止解除、別の取得経路は追加しない。

予約済みの状態・レース・払戻取得と、それに続く最初の当日オッズ取得を優先し、月次は通常の取得枠1回を使う。日次と同じ2分間隔、429待機、拒否停止、原本ハッシュ、試行・観測の保存、再配送の処理を共有する。月を跨いだETagの流用を避け、毎回本文を取得する。スイッチを無効にしたときの未着手月次枠は未取得として記録し、日次収集を続ける。途中の取得は既存の保存回復・不明通信の停止規則を先に適用する。

原本・取得証跡は非公開R2、索引はD1へ`FINAL_ONLY`として保存する。既存の当日自動解析はこの種別を対象外にし、月次の複数CSVを当日履歴へ混ぜない。最終平均への照合は取得原本の年月・競走・券種・買い目を検査した後に行う。保存準備、実取得、最終値の照合は別々に[status.md](status.md)へ記す。

## 読出しと時点

- 既存の非公開`odds` RPCで履歴・as-ofを読む。
- `races` RPCは`normalize`、`history`、`day`、軽量な予定一覧の`schedules`を提供する。dayには`date=YYYYMMDD`と`at`を明示し、その時点までにD1で公開された最新の既観測断面だけを返す。`race_id`を指定すると、その一競走だけを読む。最新の日次断面から競走が消えていれば空結果にし、以前の断面から復活させない。
- 実際の投票締切と提供元更新時刻は未確認ならnull。予定発走から推定した締切を実測時刻に置き換えない。
- 結果・払戻の表示を保存するが、取消・返還を含む精算の適合を確認するまではPaper精算に流さない。結果欄が空でも発売中とはみなさない。
- 当日オッズの取得を続けても、直前の最後の更新を取得できたという保証にはならない。確定状態が未確認の断面を「最終」と決めない。月次FINAL_ONLYと判断入力の分離は維持する。

## 固定時点のPaper

`configs/cloud-paper.json`で登録数・登録可能な期間・処理リースを調整する。既存研究Workerの`PAPER_ENABLED`を有効にした環境だけが、非公開`paper` RPCの`enroll(race_id, base_config)`と毎分Cronの判断を実行する。登録は未来の競走に限定し、三モデルの設定は実験版ごとに固定する。基準は既存の`research-shadow-near-close.yaml`で、受信から300秒、入力固定から判断完了まで30秒の上限を維持する。

判断前に公表された発走変更は、D1へ元の計画と改版時刻を残す。繰上げで新しい判断時刻に間に合わなかった場合は見送りにし、過去の購入を作らない。判断時刻までに利用可能だったオッズ・状態・レース情報だけを使う。三モデルの選択・日額上限・完了時刻は一回のD1更新で固定する。入力や詳細保存が失敗した場合も見送りを固定し、復帰後の値で再購入しない。

公式払戻が適合した後に既存規則で精算する。改訂された払戻は履歴として追記し、`history(plan_id, at)`はその時点で記録済みの判断・精算だけを返す。収集・原本保存のalarmは別Workerにあり、Paper計算の成否にかかわらず続く。

## 日次のPaper自動登録

既存devへ配置済みの研究Workerの`AUTO_PAPER_ENABLED=true`では、毎分Cronが利用可能な公式レース情報から未来の競走を登録する。`configs/cloud-paper-schedule.json`で登録範囲・間隔・会場コードを調整する。価格や結果で対象を選ばず、30分以内、判断まで10分超、他の判断から6分以上空く競走を時刻順に一つずつ検討する。登録後は同じ入力・三モデル・金額・閾値を固定する。基準設定の実験名へ`:daily-auto-v1`を付け、手動登録や既存台帳と区別する。

判断5分前の状態ページ、3分前の全場レースZIP、予定発走16分後の公式払戻ページを、既存収集担当の`scheduleEvidenceBatch`で一括予約する。共有120秒間隔・8未実行枠の上限を維持し、通常の取得枠を使う。レースZIP後の通常オッズ取得を判断に使う予定だが、通信・解析の遅延や欠測は従来の鮮度/as-of条件で見送りにする。直前配信の保証や全競走へのPaper登録ではない。当日の全場を含むZIP収集は続く。

競合時には予約を部分保存しない。発走変更では自動予約の未来・未着手枠を`SUPERSEDED_PLAN`として履歴に残し、手動枠や実行済み取得を保持する。観測予定の版を照合し、古い処理の遅着で新しい予約を取り消さない。取消済みイベントの再利用が必要な変更や、予約枠を確保できない競走は自動登録を見送る。予約後の登録失敗は、同じ予約から現在時刻で復帰し、過去の登録時刻を作らない。

初期の会場コードは保存済みの公式リンクで確認した門別・水沢・船橋・金沢・名古屋・園田・佐賀。未確認の会場は自動Paper登録を保留し、公式コードの確認後に設定へ追加する。実際の受付締切は未確認ならnull。状態や払戻の未掲載・不適合では、従来の見送り/精算待ちを維持する。翌日の実競走での自動登録・適格入力の計算・仮想購入・公式精算は別途実測する。

## 移行状況

収集DOと原本解析Workerは既存devで有効。10月1日17時台にCloudflareからの新規取得・保存・解析を確認し、Macの収集を終了した。18時台に追加分を含む308オッズ観測・レース情報15断面の原本と索引の移送が完了した。12個のローカルストアと付随証跡のアーカイブは非公開R2から読み戻し、39,410ファイルのハッシュ一致を確認済み。過去分のクラウド再解析は新着データを優先しながら進める。元の`available_at`と、Cloudflareで後から解析した版の新しい`available_at`を混ぜない。

1. Cloudflareからの公式取得は成功した。今後の拒否やCAPTCHAでは共通制御で再停止し、429では指定時間以上待つ。
2. 複数時点の取得、R2/D1保存、解析、履歴の再読出しを確認し、当日全体・翌日切替の実測を続ける。
3. Macの既存データは、元の取得時刻・解析利用可能時刻・台帳を変えずに非公開R2へ移送済み。クラウドで後から解析した版の利用可能時刻は移行後の実時計とする。
4. Macの有限収集は終了済み。旧計画を再開せず、夜の集計もCloudflareの保存結果を使う。移行途中の欠測は残す。

新規登録・メール・問い合わせ送信は行わない。実データ・詳細出力はGit・CI・PRへ含めない。
