# 当日の全量収集と競走別の追跡

## 対象と現在の状態 — 2026-09-30

地方競馬を主対象に、当日の全競馬場・全競走を含む公式オッズZIPを約2分間隔で保存する。ZIPは一度だけ取得し、既存の解析で競走・券種へ分配する。単勝から三連単まで配布された全行とレンジ・0.0の原表記を保持する。出走数に対する全組合せが揃う断面だけを分析へ使い、未掲載を0で埋めない。

中央競馬は条件に適合する取得経路が確認できた場合に追加する。地方を主対象にする最新指示に従い、中央だけを提供するTeam-Naveは候補から外した。登録・購入・投票用認証は追加しない。戦略研究は引き続き平地・Paperだけとする。

追加した一日計画はローカルの有限実測用。Cloudflareの公式取得は404後の停止を維持し、全日・常時稼働は未実測。Mac常時稼働を定常構成にはしない。

## 「約2分」の意味

[公式説明書](https://www.keiba.go.jp/pdf/manual/data_pdf_manual.pdf)の約2分は当日ファイルの更新間隔。投票締切の2分前に配信されるという意味でも、更新から受信までの遅延の上限でもない。更新と取得のタイミングがずれれば、その間の更新を観測できないことがある。約2分の取得で提供元の全更新を一つ残らず取得できるとは報告しない。

CSVには各オッズの更新時刻がなく、source_updated_atはnull。ファイル名の時刻や受信時刻を代入しない。同一ZIPから取り出した券種間の同期も保証しない。race-watchのage_secondsは受信からの経過時間であり、オッズが作られてからの経過時間ではない。freshness_basisはCOLLECTOR_RECEIPT_ONLY、provider_update_latency_bound_secondsはnullとする。

直前の実行可能性は、事前に決めた判断時刻までに受信・解析が完了した断面と、その後の公式結果で確かめる。後から最終直前の断面を選ばない。記録済みの発走予定10分前のPaperは保持し、今後は締切直前へ寄せた別版を使う。

## 締切直前のPaper

目標は、投票締切前に使える最新の更新を観測してから判断すること。ただし、その更新が最後だったかは事前には確定できない。現状の配信仕様で「締切前の最後の更新の後に必ず判断できる」とはしない。

[楽天競馬](https://keiba.faq.rakuten.net/detail/000017016)は発走予定の2分前に締切。[SPAT4](https://spat4special.jp/)は南関東4場が1分前、その他は2分前。発走までの残り時間と、使う投票経路の受付までの残り時間を分ける（2026-09-30確認）。

最初の別版は`configs/research-shadow-near-close.yaml`。Paperの締切基準をSPAT4に統一し、南関東4場は発走1分前、その他は2分前と仮定する。その60秒前に利用可能な最新断面を固定し、30秒以内に計算を終えられなければ見送る。会場ごとの入力時刻は設定へ置き、登録・判断・事後診断は一つの時刻計算を使う。これは処理時間を測るための初期値で、60秒で間に合う保証ではない。三モデルの数理・金額・購入条件はNewton版から変えず、受信鮮度の上限300秒も維持する。この上限まで古い入力を使った判断を「最後の更新を使った」とは報告せず、元観測時刻・受信からの経過・内容変化を併記する。

例えば南関東の20:00発走なら、仮定した締切19:59に対し入力は19:58、判断完了期限は19:58:30。他場なら締切19:58に対し入力19:57、完了期限19:57:30。初期設定のままでは南関東の19:58以降の更新は判断に使わない。追加の1分をさらに活用するため、処理実測に基づく余裕の短縮も検証する。後から届いた値で入力や判断を更新しない。計画の`sales_close_at`は実際の受付締切を観測できていないためnullを維持し、締切の仮定は設定と判断記録の`paper_timing_assumption`に残す。

取得・保存・解析・判断の所要時間、締切前に利用可能だった断面、鮮度不足・期限超過の見送りを実測する。結果を見て最も儲かる時刻を後選択せず、処理時間に基づき余裕を短縮する場合は次の設定版として事前登録する。実投票の送信・受付時間はPaperで測れないため、実投票可能性の確認とは分ける。詳細は[実験計画](experiment_plan.md#締切直前の探索版)にまとめる。

### SPAT4に合わせる場合の取得先

[NARの説明](https://www.keiba.go.jp/beginner/step2.html)は、各券種のオッズが投票締切まで変動するとしている。南関東はSPAT4で発走1分前まで投票できるため、2分前の値を最終値として固定できない。個別レースで2分前と1分前の公開値が必ず異なるという意味ではない。

投票経路をSPAT4に合わせても、NARの配布ZIPが速くなるわけではない。[南関東公式サイト](https://www.nankankeiba.com/)には公開の券種別オッズ一覧とSPAT4締切欄があり、登録なしで閲覧できた。ただし、締切直前の更新間隔・全組合せ・NAR ZIPに対する受信差は未実測。投票画面の認証情報を収集へ持ち込まず、公開経路の条件と完全性を確認したうえで比較する。必要な最新断面が締切前に届かない経路は、直前戦略の主入力には採用しない。

## 共通CLI

調整値は configs/collection.json。取得間隔120秒、各枠の許容遅延90秒、照会上の受信鮮度300秒を初期値とする。取得先・共有間隔・停止条件・原本保存・解析はSamplesとStoreを再利用する。

```sh
# 保存先は既存の共通rootを使用。登録時点より先の、同じJST日内を指定する。
PYTHONPATH=src uv run python -m hr_platform.cli --root private/current-state-samples/state-store day-plan \
  --from '<開始のタイムゾーン付き日時>' --until '<終了のタイムゾーン付き日時>'

# 上で返されたprivate_reportが計画ファイル。既定は1ステップだけ。
PYTHONPATH=src uv run python -m hr_platform.cli --root private/current-state-samples/state-store collect-day \
  --plan '<計画のprivate_report>' --wait-seconds 3600

# 取得とは独立した照会。詳細はprivate_reportへ保存する。
PYTHONPATH=src uv run python -m hr_platform.cli --root private/current-state-samples/state-store race-watch \
  --date '<YYYYMMDD>' --at '<照会するタイムゾーン付き日時>'
```

一日計画はオッズZIPだけを扱う。開催・出走情報や払戻は既存の共通入口で別途取得し、間隔・停止状態を共有する。他の取得と競合して枠に間に合わなければ欠測になる。取れなかった枠を現在の値で埋めない。

同じ枠の再実行は再配送として扱い、HTTP・観測を増やさない。別の枠で同じ本文を取得した場合は観測を残す。拒否で停止し、429はRetry-Afterを守る。解析失敗で後続の収集を一律に止めず、解析・保存が次枠へまたがった場合も、期限内ならその枠を処理する。PLAN_ENDEDは計画の終了であり、全枠成功や全券種完全の意味ではない。

race-watchは予定発走時刻、各券種の行数と欠落、元観測、解析利用可能時刻、受信鮮度、欠測を一覧にする。枠式の完全性と発売有無は現状未適合で、未掲載と未発売を断定して統合しない。出走情報が未取得なら完全性は不明のままにする。この照会はモデル・Paper購入・精算を起動しない。
