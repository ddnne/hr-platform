## 実行範囲

- 対象は既存の `hr-platform-dev-ingestion`、D1 `hr-platform-dev-index`、非公開R2 `hr-platform-dev-private` のみ。
- 2026-09-29 21:50 / 21:55 JST（12:50 / 12:55 UTC）に、公式の当日オッズZIPを各1回、最大2回取得する計画だった。実際は初回で停止した。間隔は5分。期日を過ぎた場合は実行せず、過去分の取得と扱わない。
- `CAPTURE_SLOTS_JSON` にこの二時刻のUTCミリ秒を指定する。CloudflareのscheduledTimeには秒が含まれるため、その属する分で枠を照合し、同じ分の再配送を同一イベントにする。期限は分起点の120秒、実取得時刻は実時計のまま保存する。本番scheduled入口は空・不正計画・予定外・予定前・120秒超の遅延では新規HTTP取得しない。保存済み原本の索引修復は、承認済み枠に限って期限後も追加取得なしで行える。
- 同一イベント再配送は既存のイベントIDで冪等化。別時刻の同じ内容は別観測として保存する。403・CAPTCHAは停止、429は既存の待機条件を守り、別経路や追加枠による回収はしない。
- 初回有効化時のみ両取得スイッチをtrueとし、5分Cronを設定する。指定日時以外は取得しない。終了確認後にスイッチfalse・Cron空へ戻す。戻す作業が遅れても、有限の二枠を超えて取得しない。
- 原本・manifest・観測を既存の非公開保存先に残す。最大圧縮量は既存上限16MiB×2。実バイト数、取得/処理時間、保存・照会件数を記録する。新規契約・プラン変更・公開範囲の変更は含めない。

## 404の原因を区別する診断取得（2026-09-29、実施済み）

最初のCloudflare応答は本文・判定ヘッダーがなく、通常のHTMLエラーと明示的challengeを区別できなかった。先に成功したMacの取得コードは研究用User-AgentとZIPのAcceptを指定していた一方、Workerは省略していた。取得場所・時刻も違うため、ヘッダーが原因だとは確定していない。

同じ公式URL・同じCloudflare devから、正直な研究用User-Agentと`Accept: application/zip`を付ける。ブラウザ名への偽装・別IPへの切替は行わない。テスト・独立レビュー後、未来枠1個だけで診断した。最初の22:45 JST予定は、Cron実呼出しを確認して22:35へ前倒しした。以前の失敗記録を残し、既知の旧404の停止状態に一致する場合だけ手動で一度解除する。新たな応答を読むまで次の取得枠は設けない。新たな拒否・challengeでは再停止を維持する。

失敗応答のHTTP状態、content-type、cf-mitigated、停止判定の根拠、本文の最大8KiBを、非公開R2の`failure-metadata/`へ保存する。本文はbase64表現でも実応答であり、Git・CI・PRには含めない。Cookie等のヘッダーを保存しない。停止フラグは本文を読む前に永続化し、診断記録の保存失敗でも解除しない。成功したオッズ観測とは別の診断資料である。


診断結果もHTTP404・text/htmlだった。cf-mitigatedヘッダーはなく、停止根拠はNON_SUCCESS_HTML。保存した本文prefixは公式の404案内で、明示的拒否は検出しなかった。末尾は保存対象外のため拒否の不存在までは断定しない。再停止後に両スイッチ・枠・Cronを解除し、公開無効を確認した。旧記録も含む失敗2件・成功観測0件である。
